01 / THE RESULT

A different text resource.
The same Japanese slot.

The starting point was a Japanese-market OM SYSTEM OM-5 Mark II with Japanese menus. The goal was an English interface while changing as little of the camera's firmware as practical.

The official firmware already contains English text. This experiment builds a new string resource from it and directs the Japanese language record to that resource. The original Japanese font is retained. Where the English table has an empty entry and the Japanese table has text, the build supplies one of 39 explicitly identified research translations.

The owner installed the resulting resource-only package once and reported that the camera booted normally with English menus. Subsequent functional testing was partial, with no problem reported in the unspecified subset tried.

0101

The only component included in the experimental package: resources.

4,909

String IDs in the native table; English text plus 39 research additions.

12 MiB

The entire resource range selected for erase/write, despite the narrow edit.

Exact scope: native E148 / OM-5 Mark II / official 1.1. The original OM-5 (E144), cross-model Mark II ports and other builds are outside this result. English text in the Japanese slot does not demonstrate an unlocked language selector or changed factory region.

02 / THE RESEARCH PATH

From a localization lead
to a single physical trial.

  1. Separate the targets. Identify the camera and pin the official native E148/1.1 input. Keep original OM-5 and ported firmware evidence separate.
  2. Learn from the existing projects. OMKit and Caduceus supplied format and native-platform references. db firmware's localization work suggested studying language resources. Its closed patcher was not executed and did not generate this candidate.
  3. Make the smallest understood resource change. Parse stock resources, build an English-based string table, retain the Japanese font and change the Japanese descriptor. Verify all other resources and executable components stay unchanged.
  4. Test and review offline. Exercise failure cases, reproduce the bytes with an independent encoder, run selected native paths in OM-Emu and complete six AI-assisted review rounds. Record the emulator's substitutions and unresolved startup/recovery behavior.
  5. Establish a working stock baseline. The owner first completed the official 1.0 → 1.1 update through OI.Share. The app again reported OM-5MarkII / 1.1. The owner confirmed normal baseline functions and Japanese menus.
  6. Perform one explicitly approved trial. After the exact file and reviewed procedure were approved, the owner operated the camera's SD updater. The reported lamp sequence was steady, then blinking. A later normal boot without the update card showed English menus, according to the owner.
  7. Preserve the limits of the result. The update file was removed and its absence checked. The owner reported only a partial functional pass. No second installation or destructive recovery experiment followed.

The hardware report summarizes the historical r01 trial and cites OMKit's description of the updater. The reviewed r01 trial procedure is not included in this export. OMKit's loader installation instructions are not this experiment's procedure. The original one-trial permission does not authorize another installation.

Reuse English. Preserve the font.
Redirect one descriptor.

Select the new tableJapanese font · record 28 · unchanged

Logical diagram; these are resource records, not instructions to write device memory.

The builder copies the original English text area and pointer table. In the new table, 4,870 pointer values stay unchanged and 39 point to the added translations. The original English resource itself remains untouched. Japanese font metadata is retained, and icon escapes and special controls must remain in the same order. The new table is placed in verified zero-filled reserve, aligned to the native reader's requirements.

Only two decoded ranges change: the Japanese descriptor's eight source/span bytes and the appended table. The resource trailer checksum is recomputed. The full intermediate image is checked, then only component 0101 is extracted into the resource-only output.

The code does not rewrite the camera's region configuration, calibration, bootloader or language policy, and the installed package contains no OMKit loader. Keeping those changes out reduces scope; it does not make the resource erase/write harmless.

Full offsets, expected bytes and algorithm: design report. Function-level detail and rejection rules: agent context.

Offline tests cover malformed containers, bounds, checksums, resource and string parsing, translation coverage, controls, size limits and refusal of unexpected inputs. The export records its actual test and reconstruction result in publication-validation.json.

Earlier native-code experiments used OM-Emu with synthetic settings, substituted resource reads and modeled peripherals. Some UI/startup paths remained unresolved for both stock and candidate. The central risk remains the write itself. The analyzed updater erases the entire 12 MiB resource range before programming. Whether its recovery path is usable after damaged resources remains unknown. The stock resource reference is not an independent rescue loader.

05 / USING THE PACKAGE

Start offline.
No camera is needed.

1. Open and inspect

Download the source package and open START_HERE.html in a browser. This page uses no external fonts, scripts, analytics or network requests. GitHub's file view may display its source; open the downloaded file locally to see the formatted guide.

The package contains Python code, tests, reports, hashes and the 39 original research translations. Firmware must be obtained separately. Compare package files against SHA256SUMS if checking integrity; hashes do not establish authorship or hardware safety.

2. Run the tests without firmware

Use Python 3.9 or later, with its standard library only. Run commands from the package root; no dependency installation is needed. The recorded validation environment used Python 3.9.13.

python -B -m unittest discover -s tests -v

Expected without a stock input: 41 tests run, 39 pass, 2 skip. Those two skips are the integration tests; they do not mean the firmware rebuild has been checked.

3. Reproduce in memory

Supply the exact official E148/1.1 file whose size and SHA-256 are listed below. Replace the example path with its location on your computer. Preserve the stock file.

python -B tools/reproduce.py --stock /path/to/stock.BIN

The command builds and verifies r01 in memory, then prints a JSON report. With no output option, it writes no firmware. Expected fields include the pinned resource hash, resource_bytes: 12582912, string_count: 4909, research_translation_count: 39, files_written: 0 and hardware_safety_proven: false.

4. Run the two integration tests

PowerShell:

$env:OM5_TEST_STOCK='D:\firmware\stock.BIN'
python -B -m unittest discover -s tests -v

POSIX shell:

OM5_TEST_STOCK=/path/to/stock.BIN python -B -m unittest discover -s tests -v

With the pinned input, the recorded result was 41/41 passing. Record your Python version, code revision, hashes and any failures or skips.

5. Save research outputs only if needed

python -B tools/reproduce.py --stock /path/to/stock.BIN --output-dir /path/to/new-research-output

The output directory must not exist and its parent must exist. Choose an ordinary local research location outside the repository and any publication archive. It receives:

  • JP_EN_resources.research-bin — the pinned r01 resource-only output.
  • STOCK_resources.research-bin — the matching stock resource reference.
  • build.json — input/output hashes and construction details.

The tool first writes temporary files under .INCOMPLETE, closes them and checks their disk sizes and SHA-256 values. Final names appear only after the entire set passes those checks. The marker directory is removed last. If an error leaves .INCOMPLETE, treat the whole set as unfinished; a failure during final renames can leave some verified files alongside it. Inspect the directory before another offline run in a fresh location.

The tool has no camera transport, automatic installation, SD discovery or updater filenames. Its path checks are not a device sandbox: explicitly choose a local disk path, not a camera or removable card. Host disk readback does not verify flash inside a camera.

If a check refuses the input, investigate. A different version, partial package, damaged input or edited translations must not pass as this r01. Do not disable a digest check or change the expected hash merely to continue. Exit 0 confirms reproduction; it is not installation approval.

07 / QUESTIONS BEFORE GOING FURTHER

What this package cannot promise.

Can I install it on my camera now?

This package provides reproducible research and one scoped physical report. It does not supply a generally validated installation release or automatic installer. Another hardware trial requires its own exact target, file, reviewed procedure, explicit owner decision and acceptance that recovery may be unavailable. The existing owner's one-trial approval has already been used.

Does “resource-only” mean it cannot brick the camera?

No. The selected resource area is erased and rewritten, and startup may depend on its contents. A power or write failure, corruption or an untested resource path could leave a camera unusable. Recovery after damaged 0101 remains unknown. No destructive failure test was performed.

Is all of the English official?

Most text comes from the existing firmware English table. The 39 gap entries are research-authored translations, separately listed in the package. Their reachability, wording, line breaks and layout still need review. English font coverage and valid pointers do not establish complete UI correctness.

Can I change a translation or use another firmware version?

That produces a different experiment. The current build is deliberately pinned and will reject an unexpected result. A new variant needs separate input identification, bounds/token/layout checks, hashes and review. E144 and Mark II ports are not interchangeable with native E148.

Will a later official update preserve English?

Not established. A future update could replace resource data or change the layout. Do not reuse this candidate across builds or assume its effect survives an official update.

Why not publish the firmware itself?

The useful shareable result is the transformation, its exact identity and the evidence. Recipients supply their own official input. No proprietary firmware, full vendor string tables, fonts, dumps or closed patcher are included. Generated research binaries should remain outside published source archives.

08 / WHERE TO GO NEXT

Make the evidence stronger.

The most useful next steps are independent byte-for-byte reproduction, review of the 39 translations, specific ordinary-use observations from the already-tested camera, and offline study of startup and recovery dependencies.

A useful report gives the exact model/build, source revision, input/output hashes, environment, steps checked, pass/fail/skip results and remaining uncertainty. Keep what you directly measured separate from owner reports, upstream claims and inference. Do not include serial numbers, accounts, network/card identifiers, credentials, personal metadata, firmware or full chat histories.
